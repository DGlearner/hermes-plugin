# 日报草稿工作流接入

本次隔离版本新增员工日报技能和 Hermes 确认保护。部署前须配套发布后端日报草稿、模板检查和发布接口。
生产启用状态应以实际部署和验收结果为准，本文件不作为已上线的证明。

## 员工使用流程

员工在企业微信、个人微信或 Telegram 发送文字草稿，Hermes 获取后端集中维护的八节模板，读取同一日期和归属的本人当前草稿，整理事实并保存。
检查返回具体缺口时只追问对应事实；检查通过后完整展示服务器返回的正文，提示员工回复 **确认提交日报**。
员工在之后一条消息中单独回复该短语，才可发布那一版正式日报。正式日报修改执行同一流程。

草稿与正式日报分开，检查通过不自动发布。草稿保存或检查不会触发正式日报推送。
模板正文和业务规则分别见 [daily-report-template.md](daily-report-template.md) 和 [daily-report-validation.md](daily-report-validation.md)。
运行时以 `get_daily_report_template` 返回的模板、版本和规则为准，技能中不维护第二份模板正文。
企业微信入口当前只处理文字，不能把未接入的图片或文件当作已分析的事实来源。

## 工具和确认边界

| 工具 | 行为 |
|---|---|
| `get_daily_report_template` | 读取权威模板和版本 |
| `get_daily_report_draft` | 读取本人草稿及版本；可用 `draft_id` 或目标 `report_id` 精确定位 |
| `prepare_daily_report_draft` | 保存草稿；已有草稿使用 `draft_id` 和 `expected_draft_version`；改动使旧检查失效 |
| `validate_daily_report_draft` | 检查确切版本；通过时返回短期凭据和正文摘要 |
| `publish_daily_report_draft` | 使用通过版本、凭据、摘要及固定重试标识发布 |
| `submit_daily_report` / `update_daily_report` / `save_daily_report_draft` | 旧写入入口被拒绝，必须转新草稿流程 |

部门、公司日报保留同日多篇能力：修改必须用 `report_id` 指向具体日报，省略表示新建。
旧系统草稿通过 `list_daily_report_drafts` 读取后，可将其 `report_id` 和正文传入 prepare 导入新流程。

后端负责员工权限、草稿版本、模板版本、正文摘要、检查结果、短期凭据和重复请求检查。
Hermes 的 `report_workflow.py` 另外通过原生 `pre_llm_call` / `post_llm_call` 钩子核对员工确认：

- 确认状态绑定当前员工 Profile、Session、平台和发信人。
- 检查通过的确切完整正文必须出现在结束该轮的助手回复中，并附“确认提交日报”提示。
- 之后的真实员工消息必须单独为“确认提交日报”；模型参数、同轮调用、草稿内的指令和笼统“好”不构成确认。
- 发布参数必须与通过的草稿 ID、版本、凭据和摘要一致。修改或重新检查会清除之前确认。
- 同次结果不确定的发布重试必须使用相同 `idempotency_key`，防止生成新的提交请求。
- 新会话、换通道、其他员工、子任务或无员工来源的定时调用不能借用确认状态。

确认保护保存在进程内，最多保留一小时；重启后或发送其他消息后需重新检查、完整预览和确认。
后端凭据可能更早失效，后端仍会拒绝过期发布。该钩子确认的是完整回复已生成及之后的员工明确指令，
不把消息发送回执等同于员工阅读。其他直接 MCP 客户端也必须自行收集预览后的明确确认，不能依赖 Hermes 的会话状态。

## 现有员工及后续员工的覆盖

插件注册时，`install_profile_skills` 扫描当前 Hermes 根目录的 `profiles/`，向身份标记匹配的现有员工及
`employee-template` 原子安装 `skills/profile-daily-report/SKILL.md`。
不读取或复制其他员工的凭据、会话、草稿、巡检状态，其他技能保持原样。

原生技能发现的 `_skills_dir()` 在每次解析当前 Profile 时检查这份技能；因此插件启动之后新创建、
新绑定的员工首次发现技能时也会安装，无需再次重启。
安装拒绝不匹配的身份标记或符号链接目标，重复运行只更新内容确实变化的本技能文件。
已有的跨员工技能位置隐藏规则继续生效。员工常驻提示也要求日报操作加载本技能并遵守检查及确认流程。
Hermes 会把常驻提示冻结在新会话中；已经缓存提示的旧会话可能要到会话轮换后才看到新提示。
服务端和工具 handler 的检查不依赖旧提示更新，旧直写调用仍会被拒绝并给出草稿流程说明。

插件与后端应作为同一次功能发布验收。动态工具目录仍由服务器提供，打包目录只是服务端目录读取失败时的缓存。
若服务器尚无新工具，日报只能说明暂不可提交，不能回退到旧直写。

## 隔离验收

`python3 -m unittest discover -s tests -p test_report_workflow.py -v` 使用临时目录和伪服务端返回，
覆盖三种平台的真实后续确认、同轮阻止、完整预览、失败检查、跨员工／会话隔离、重启与定时任务、
改稿失效、旧直写拒绝、重复发布标识以及现有／新增员工技能安装。
该测试不调用业务服务，不发送消息，不修改生产员工目录。

`tests/test_report_workflow_runtime.py` 在原生 Hermes 内通过真实 `PluginContext` 注册插件，
执行 `PluginManager.invoke_hook` 和 `Registry.dispatch`，验证三个平台的真实钩子参数、
Profile／Session 对应关系、后续确认和完整预览保护。测试后端响应为本地伪数据。
可在断网的一次性 `nousresearch/hermes-agent:v2026.8.31` 容器中以 stdlib unittest 运行，
只读挂载本候选源码，使用临时 `HERMES_HOME`；无需生产员工数据或真实消息。

发布验收还须结合后端测试确认：不合格草稿拒绝发布、合格内容保存不推送、确认后只发布一次、
正式修改重新检查、权限范围不扩大，并在绑定员工的受控会话验证完整预览与确认交互。
