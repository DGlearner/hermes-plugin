# 上传人的审核结果通知

`daily_inspection.main` 在现有员工巡检任务中调用 `review_result_delivery`。
它沿用该员工的启用状态、工作时段、免打扰和巡检间隔，使用独立状态库。
`include_review_results` 未配置时默认为 `true`；显式关闭仍生效。
不要求员工拥有审核权限，也不依赖 `include_reviews`。日报查询失败不会阻止本人的审核结果通知。

## 内容与接收范围

每轮以员工 Profile 的 PAT 校验 `get_current_user`，从第一页读取全部待通知结果。
后端限定当前员工本人上传的版本，管理员也不能查询或确认他人的通知。
只有完整分页校验通过后才发送，下一轮始终从第一页开始，避免遗漏较晚提交的审核事务。

批准、驳回均通知，固定文字包含文件名、标题、知识编号、版本、结果、审核人、审核时间和完整原因。
不调用模型，也不执行文件名或原因中的指令。长内容按 UTF-8 字节数分段并编号。
企业微信采用既有 markdown 推送通道的 4000 字节预算；同时有微信或其他通道时采用 1900 字节预算。
此通知无需员工回复“已读”。

接收人只来自当前 Profile 已绑定的单聊通道，所有配置目标须与启用中的路由一致。
首次投递时固定通知内容、分段、批次号、目标和绑定身份。绑定变化后保留原通知并暂停该条处理，
不会把旧消息自动改发到新对象。

## 送达状态

状态存放在 `inspection/review-results/state.sqlite3`，目录权限 0700、数据库权限 0600。
每个 Profile 有独立的进程锁；既有 `inspection/deliveries.sqlite3` 继续按批次、分段、平台、目标去重。

| 情况 | 处理 |
| --- | --- |
| 所有目标的所有分段明确发送成功 | 保存 `sent`，调用后端 ACK，成功后转为 `acked` |
| 发送成功，ACK 失败或超时 | 保留 `sent`，下个巡检只补 ACK，不重发消息 |
| 企业微信明确拒绝、连接未建立或发送前失败 | 记录 `rejected`，下个巡检仅重试被明确拒绝的分段 |
| 已尝试发送，但响应超时、异常或不可验证 | 保留 `unconfirmed`，不 ACK、不自动重发 |
| 进程在发送中退出 | 恢复后保留 `unconfirmed`，等待人工核实 |
| 查询失败或分页不完整 | 本轮不发送、不 ACK，下个巡检重新查询 |
| 未绑定、禁用或不在允许时段 | 不发送 |

`retry_rejected=True` 只由新审核结果通知使用，现有日报、任务和待审核提醒的重试规则不变。
未知通道错误仍按发送结果不确定处理，不推断为安全重试。
Hermes 的模型工具入口禁止调用送达 ACK；原生通知流程在确认成功后直接调用 MCP。
后端 ACK 信任认证客户端对平台回执的确认，不代表员工已阅读。

外部通信平台和本地/后端数据库之间没有跨系统事务。本实现保留不确定状态，优先避免盲目重发；
`unconfirmed` 和 `binding_changed` 需要人工核实后再处理，本次未加入自动补发或清理规则。
`last_result.json` 只包含计数、状态和时间，不包含审核原因、文件名或凭据。

## 第 3 步交付边界

此阶段仅在隔离工作树实现并测试，未修改现网配置、部署或发送员工消息。
迁移 051、052 都不扫描历史事件。指定历史记录的补发按发布授权单独处理。
